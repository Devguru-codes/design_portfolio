Opportunity type: Disruptive

Retrieval-augmented generation treats hallucination as something to be discouraged — better prompts, better reranking, a confidence score. Callosum treats it as something to be refused. A fact that cannot be traced to a verbatim sentence in a source document never enters storage at all. That is a different product category, not a better version of the same one.

Executive summary

This project began as a pre-internship product assignment: evaluate whether Meridian, an operating system for startups, should build a board management module. The research said the interesting problem was not running board meetings. It was everything that happens between them — the decisions that get made, then lost.

I produced thirteen deliverables covering market and user research, a competitor teardown, a prioritisation matrix, a build-versus-buy analysis, a three-phase roadmap and a full PRD for the V1 MVP, then built a clickable prototype to make the argument tangible. That work became the specification for Callosum: a working system with a knowledge graph, a vector store, and a verification gate between the model and the database.

The system is named for the corpus callosum, the fibre bundle joining the brain's two hemispheres. Callosum has two hemispheres as well — a graph and a vector store — and the bridge between them is the entire idea.

The problem

Problem statement

Founders don't struggle with running board meetings. They struggle with preserving, retrieving and acting on board knowledge over time. Documents scatter across email, Drive, Notion and slide decks; the reasoning behind a decision lives in a transcript nobody re-reads. Our research put the cost at 15–20 hours of context reconstruction before each board meeting.

The obvious fix — point an LLM at the document pile — fails for exactly the questions that matter. Ask "why did we reject Pricing Model B?" and a conventional RAG system will produce a fluent, plausible, unverifiable paragraph. In a governance context that is worse than no answer, because a fabricated rationale attributed to a named director is a liability, not a convenience.

So the product requirement was unusual: the system must be able to say "I don't know", and it must be structurally incapable of inventing the alternative.

Discovery: research before design

Before any interface existed, I worked through the board lifecycle end to end. The deliverables are public in the research repository.

Use cases and prioritisation

I mapped eight high-value use cases across the lifecycle and scored them on an impact-versus-engineering-effort matrix:

  • Pre-meeting: AI meeting preparation, agenda building, board-pack assembly.
  • During: live meeting intelligence, decision capture as it happens.
  • Post-meeting: resolution management, commitment tracking.
  • Across time: institutional memory — the one that turned out to be the product.

The build-versus-buy analysis recommended reusing Meridian's existing authentication, notifications and shared context layer, and building only the differentiated pieces: the decision engine and the meeting workspace. Everything else was someone else's solved problem.

Prototype: making the argument tangible

A PRD persuades nobody on its own. I built a full clickable prototype — dashboard, AI agenda builder, board pack view, decision capture, live meeting interface and the institutional memory screen — using AI tooling to compress what would otherwise have been weeks of mockup work into a working artifact that could be clicked through in a review.

Using generative tooling for fidelity is, I'd argue, a product skill rather than a shortcut. From prototype to system

Callosum is the prototype's memory screen, built for real. Two stores, bridged by a shared chunk UUID: a chunk row in Postgres and its node in Neo4j carry the same identifier, so a vector hit can traverse into the graph, and a graph hit can pull back the passage that proves it.

The invariant that makes it work

The rule the whole system rests on

No relationship enters the graph without a verbatim quote that a string search located in the source document.

This is the design decision I'm proudest of, because it moves the guarantee out of the model's hands entirely. The verifier is not a judgement call, a second model, or a confidence threshold — it is a character-for-character search. It tolerates the ways a faithful quote's bytes can legitimately differ: whitespace reflow, casing, typographic glyph substitution. Nothing else.

A paraphrase is treated as a fabrication. The model is free to hallucinate as much as it likes; the hallucination simply cannot become memory.

Rejections are kept, not dropped

Failed edges are quarantined with a typed reason rather than silently discarded. This was a product decision, not a technical one. "This model fabricates a quote on 8% of the relationships it marks approved" is a finding you can act on — and you can only make it if you kept the failures. Dropping them would have made the system look cleaner and told us nothing.

Access control as a design decision

A board pack contains material that not every reader should see. The conventional approach is to retrieve everything and hide the sensitive rows in the interface. That leaks: the shape of what was hidden is usually enough to infer its content.

Callosum filters before retrieval, in SQL and in Cypher, at the caller's own clearance level. Surviving items are renumbered from 1, so a lower-cleared reader sees a shorter list with no gap in the numbering to count.

Two withholding contracts, deliberately different

The graph view discloses a count of withheld items. Board packs disclose nothing at all. That inconsistency is intentional and took the longest to settle: a notice that appears only when something is hidden is itself a disclosure. On a page where a count is always shown, showing it is safe. On a page where it would appear selectively, it is not.

Constraints over conventions

One finding was genuinely surprising. Postgres validates foreign keys as the table owner, which bypasses row-level security — so a single-column reference can link two tenants through a constraint neither of them can read across. We reproduced it as an attack, then fixed it with composite (id, workspace_id) keys that reject it even through a superuser connection, covering 16 relationships across 14 tables.

There is a second half to that story worth telling: the migration rewrote 16 keys but gave only 11 an explicit delete behaviour, so cascade semantics silently changed until a follow-up migration restored them. The fix needed a fix. That is what security work actually looks like.

Relatedly, two field names are never accepted from a client — and rather than rely on reviewers remembering that, the build walks the generated API schema and fails if either name appears anywhere, including nested inside a request body. Code review is the wrong instrument here: an endpoint that takes a workspace filter looks completely ordinary, and the harm is invisible at the call site.

All of the loss sits in one stage. The right entity was offered every single time and traversal never failed once seeded, so the bottleneck is named entity linking — not the graph, and not retrieval. That measurement is also why a planned abstention algorithm was never built: instrumenting the pipeline removed the reason for it. Measuring first saved building the wrong thing.

These numbers are not current

They come from a run dated 20 July 2026 against a 29-item gold set. That set has since grown to 46 items, and seven of the questions in it have never been measured. Grounding precision of "50%" is one item out of two — the gold set now carries four abstention negatives, so that denominator doubles the moment it is re-run.

The figures are correct for what they measured. They are not a current characterisation of the system, and I'd rather publish that sentence than a number that quietly implies otherwise.

That em-dash rule is a small interface decision with an outsized effect on trust. A dashboard that shows 0% for something it simply hasn't computed is lying in a way users cannot detect. Showing — costs nothing and keeps the interface honest about the difference between zero and unknown.

One phase is frozen, not accepted

Of the three exit criteria for the product's third phase, one was met, one was partial and one was not met — the accessibility and error-state checkpoints were deliberately deferred. That is recorded as a freeze rather than rounded up to a pass. A roadmap that only ever reports green is not a roadmap.

Limitations

  • The corpus is synthetic. Sixteen authored documents, no real organisational data. Everything above is measured on a corpus we wrote.
  • Accessibility is designed but unaudited. The interface was built to a spec; no audit has been run against it.
  • Single run. The results have no multi-run stability characterisation, so run-to-run variance is unknown.
  • Grounding precision is thinly measured — one abstention case out of two, as above.

What I'd do differently

Instrument earlier. The stage-by-stage evaluation is what told us the bottleneck was entity linking rather than the graph, and it arrived after a planned abstention algorithm had already been specified. Had it existed a month sooner, that specification would never have been written.

Keep the evaluation and the gold set in step. The most honest thing on this page is also the most avoidable: the gold set grew while the published figures did not. The gap is documented and tracked, but the right answer was to make re-running the evaluation cheap enough that it never drifted.

Decide the withholding contracts up front. The graph-versus-board-pack disclosure asymmetry is correct, but we reached it by argument after both pages existed. It should have been a written contract before either was designed.
